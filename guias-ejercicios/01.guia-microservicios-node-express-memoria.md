# Guía práctica: tres APIs REST con Node.js y Express

## Cliente, Producto y Compra, con validación entre servicios

---

## Objetivos de aprendizaje

Con esta guía buscamos que el estudiante logre:

- Diseñar un sistema con varias APIs independientes que se comunican entre sí por HTTP.
- Configurar las URLs de otros servicios como variables de entorno, en lugar de escribirlas fijas en el código.
- Implementar un endpoint que valide, antes de crear un recurso, que otros recursos relacionados existan (Compra valida Cliente y Producto).
- Manejar errores propios de la comunicación entre servicios: recurso no encontrado, servicio caído, datos inválidos.
- Ejecutar y probar varios servicios corriendo al mismo tiempo en puertos distintos.

---

## 1. Arquitectura general

Vamos a construir tres APIs separadas, cada una con su propia carpeta, su propio `package.json` y su propio proceso de Node corriendo en un puerto distinto:

```
sistema-compras/
├── cliente-api/     (puerto 3001)
├── producto-api/    (puerto 3002)
└── compra-api/      (puerto 3003)
```

La idea central es esta: cuando alguien crea una compra, `compra-api` no puede confiar a ciegas en que el `clienteId` y el `productoId` que le enviaron existen de verdad. Antes de guardar la compra, le pregunta a `cliente-api` "¿existe este cliente?" y a `producto-api` "¿existe este producto, y tiene stock suficiente?". Solo si ambas respuestas son positivas, `compra-api` guarda la compra.

Esto es justamente lo que hace un sistema de microservicios en el mundo real: cada API es dueña de sus propios datos, y cuando necesita información de otro dominio, se la pide a la API correspondiente en vez de duplicarla.

## 2. cliente-api

### Estructura

```
cliente-api/
├── src/
│   ├── data/
│   │   └── clientes.js
│   ├── routes/
│   │   └── clientes.routes.js
│   └── server.js
├── .env
├── .env.example
├── .gitignore
├── package.json
```

### Inicialización

```bash
mkdir cliente-api
cd cliente-api
npm init -y
npm install express dotenv
npm install --save-dev nodemon
```

Agreguen los scripts de siempre en `package.json`:

```json
"scripts": {
  "start": "node src/server.js",
  "dev": "nodemon src/server.js"
}
```

### Variables de entorno

Archivo `.env`:

```
PORT=3001
```

Archivo `.gitignore`:

```
node_modules/
.env
```

### Datos en memoria

Archivo `src/data/clientes.js`:

```javascript
let clientes = [
  { id: 1, nombre: "Laura Gómez", email: "laura.gomez@example.com" },
  { id: 2, nombre: "Andrés Ruiz", email: "andres.ruiz@example.com" }
];

module.exports = clientes;
```

### Rutas

Archivo `src/routes/clientes.routes.js`:

```javascript
const express = require("express");
const router = express.Router();
const clientes = require("../data/clientes");

let siguienteId = 3;

// GET /clientes
router.get("/", (req, res) => {
  res.status(200).json(clientes);
});

// GET /clientes/:id
router.get("/:id", (req, res) => {
  const id = Number(req.params.id);
  const cliente = clientes.find((cliente) => cliente.id === id);

  if (!cliente) {
    return res.status(404).json({ mensaje: "Cliente no encontrado" });
  }

  res.status(200).json(cliente);
});

// POST /clientes
router.post("/", (req, res) => {
  const { nombre, email } = req.body;

  if (!nombre || !email) {
    return res
      .status(400)
      .json({ mensaje: "Los campos 'nombre' y 'email' son obligatorios" });
  }

  const nuevoCliente = { id: siguienteId++, nombre, email };
  clientes.push(nuevoCliente);
  res.status(201).json(nuevoCliente);
});

module.exports = router;
```

Dejamos por fuera `PUT` y `DELETE` a propósito: ya vimos ese patrón completo en la guía del catálogo de libros. Como ejercicio, agréguenlos aquí siguiendo la misma estructura.

### Servidor

Archivo `src/server.js`:

```javascript
require("dotenv").config();
const express = require("express");
const clientesRoutes = require("./routes/clientes.routes");

const app = express();
const PORT = process.env.PORT || 3001;

app.use(express.json());
app.use("/clientes", clientesRoutes);

app.get("/", (req, res) => {
  res.status(200).json({ mensaje: "cliente-api activa" });
});

app.listen(PORT, () => {
  console.log(`cliente-api escuchando en el puerto ${PORT}`);
});
```

## 4. compra-api

Esta es la API donde realmente se ve el patrón que nos interesa: antes de guardar una compra, consulta a las otras dos.

### Estructura

```
compra-api/
├── src/
│   ├── data/
│   │   └── compras.js
│   ├── services/
│   │   ├── clienteService.js
│   │   └── productoService.js
│   ├── routes/
│   │   └── compras.routes.js
│   └── server.js
├── .env
├── .env.example
├── .gitignore
├── package.json
```

Noten la carpeta nueva, `services/`. Ahí va a vivir la lógica que le habla a `cliente-api` y a `producto-api`. La separamos de `routes/` porque su responsabilidad es distinta: `routes/` recibe peticiones HTTP de afuera, `services/` hace peticiones HTTP hacia afuera.

### Inicialización

```bash
mkdir compra-api
cd compra-api
npm init -y
npm install express dotenv
npm install --save-dev nodemon
```

No instalamos ninguna librería adicional para hacer peticiones HTTP. Desde Node 18, `fetch` viene incluido de forma nativa, así que lo usamos directamente sin agregar axios ni node-fetch como dependencia.

Mismos scripts en `package.json` que en las otras dos APIs.

### Variables de entorno

Aquí está la parte central de esta guía. Archivo `.env`:

```
PORT=3003
CLIENTE_API_URL=http://localhost:3001
PRODUCTO_API_URL=http://localhost:3002
```

Archivo `.env.example`:

```
PORT=3003
CLIENTE_API_URL=http://localhost:3001
PRODUCTO_API_URL=http://localhost:3002
```

`compra-api` nunca debería tener escrito en su código en qué dirección vive `cliente-api` o `producto-api`. Hoy las tres corren en nuestra máquina local, pero cuando lleguemos a contenedores (la siguiente entrega del curso), esas URLs van a cambiar, porque cada servicio va a tener su propio nombre de host dentro de la red de Docker. Si esas direcciones estuvieran fijas en el código, tocaría modificar y volver a desplegar `compra-api` cada vez que algo cambie. Con variables de entorno, solo cambiamos el `.env` (o la configuración del contenedor) y el código queda intacto.

### Datos en memoria

Archivo `src/data/compras.js`:

```javascript
let compras = [];

```

### Servicios que consultan las otras APIs

Archivo `src/services/clienteService.js`:

```javascript
const CLIENTE_API_URL = process.env.CLIENTE_API_URL;

async function obtenerCliente(id) {
  const respuesta = await fetch(`${CLIENTE_API_URL}/clientes/${id}`);

  if (respuesta.status === 404) {
    return null;
  }

  if (!respuesta.ok) {
    throw new Error(`cliente-api respondió con estado ${respuesta.status}`);
  }

  return respuesta.json();
}

module.exports = { obtenerCliente };
```

Archivo `src/services/productoService.js`:

```javascript
const PRODUCTO_API_URL = process.env.PRODUCTO_API_URL;

async function obtenerProducto(id) {
  const respuesta = await fetch(`${PRODUCTO_API_URL}/productos/${id}`);

  if (respuesta.status === 404) {
    return null;
  }

  if (!respuesta.ok) {
    throw new Error(`producto-api respondió con estado ${respuesta.status}`);
  }

  return respuesta.json();
}

module.exports = { obtenerProducto };
```

Fíjense en el mismo patrón en ambos archivos: si el otro servicio responde 404, devolvemos `null` (el recurso no existe, pero la comunicación funcionó bien). Si responde cualquier otro error, lanzamos una excepción, porque ahí sí hubo un problema real de comunicación que `compra-api` no puede resolver por sí sola.

### Rutas

Archivo `src/routes/compras.routes.js`:

```javascript
const express = require("express");
const router = express.Router();
const compras = require("../data/compras");
const { obtenerCliente } = require("../services/clienteService");
const { obtenerProducto } = require("../services/productoService");

let siguienteId = 1;

// GET /compras
router.get("/", (req, res) => {
  res.status(200).json(compras);
});

// GET /compras/:id
router.get("/:id", (req, res) => {
  const id = Number(req.params.id);
  const compra = compras.find((compra) => compra.id === id);

  if (!compra) {
    return res.status(404).json({ mensaje: "Compra no encontrada" });
  }

  res.status(200).json(compra);
});

// POST /compras
router.post("/", async (req, res) => {
  const { clienteId, productoId, cantidad } = req.body;

  if (!clienteId || !productoId || !cantidad) {
    return res.status(400).json({
      mensaje: "Los campos 'clienteId', 'productoId' y 'cantidad' son obligatorios"
    });
  }

  let cliente;
  let producto;

  try {
    cliente = await obtenerCliente(clienteId);
    producto = await obtenerProducto(productoId);
  } catch (error) {
    return res.status(503).json({
      mensaje: "No se pudo validar la compra porque uno de los servicios no respondió",
      detalle: error.message
    });
  }

  if (!cliente) {
    return res.status(404).json({ mensaje: `El cliente ${clienteId} no existe` });
  }

  if (!producto) {
    return res.status(404).json({ mensaje: `El producto ${productoId} no existe` });
  }

  if (producto.stock < cantidad) {
    return res.status(400).json({
      mensaje: `Stock insuficiente. Disponible: ${producto.stock}, solicitado: ${cantidad}`
    });
  }

  const nuevaCompra = {
    id: siguienteId++,
    clienteId,
    productoId,
    cantidad,
    total: producto.precio * cantidad,
    fecha: new Date().toISOString()
  };

  compras.push(nuevaCompra);
  res.status(201).json(nuevaCompra);
});

module.exports = router;
```

**Puntos clave**

- La validación ocurre antes de tocar el arreglo `compras`. Si cliente o producto no existen, la compra ni siquiera se intenta crear.
- Usamos `503 Service Unavailable` cuando el problema no es que el recurso no exista, sino que no pudimos ni siquiera preguntarle a la otra API (está caída, no responde, hay un error de red). Es un código distinto al 404, y vale la pena que los estudiantes noten la diferencia: 404 es "pregunté y me dijeron que no existe"; 503 es "no logré preguntar".
- El `total` de la compra se calcula con el precio que devuelve `producto-api`, no con un precio que el cliente de la API nos hubiera enviado. Esto evita que alguien manipule el precio desde la petición de compra.

### Servidor

Archivo `src/server.js`:

## 6. Pruebas con curl

### Caso exitoso

```bash
curl -X POST http://localhost:3003/compras \
  -H "Content-Type: application/json" \
  -d '{"clienteId":1,"productoId":2,"cantidad":3}'
```

`compra-api` va a consultar a `cliente-api` (¿existe el cliente 1?), luego a `producto-api` (¿existe el producto 2 y hay al menos 3 unidades?), y si todo está bien, va a devolver la compra creada con el total ya calculado.

### Cliente inexistente

```bash
curl -X POST http://localhost:3003/compras \
  -H "Content-Type: application/json" \
  -d '{"clienteId":99,"productoId":1,"cantidad":1}'
```

Esperen un `404` con el mensaje indicando que el cliente 99 no existe.

### Producto inexistente

```bash
curl -X POST http://localhost:3003/compras \
  -H "Content-Type: application/json" \
  -d '{"clienteId":1,"productoId":99,"cantidad":1}'
```

### Servicio caído

Detengan `producto-api` (con Ctrl+C en su terminal) y repitan una compra válida:

```bash
curl -X POST http://localhost:3003/compras \
  -H "Content-Type: application/json" \
  -d '{"clienteId":1,"productoId":1,"cantidad":1}'
```

Ahora deberían recibir un `503`, porque `compra-api` no logró comunicarse con `producto-api`. Este ejercicio es útil para que los estudiantes vean con sus propios ojos qué pasa cuando un servicio del que dependemos no está disponible.

## 7. Buenas prácticas aplicadas en esta guía

- Cada API es responsable únicamente de sus propios datos; ninguna guarda una copia de los datos de otra.
- Las URLs de los servicios externos viven en variables de entorno, nunca escritas fijas en el código.
- Se distingue entre "el recurso no existe" (404) y "no pude comunicarme con el servicio" (503).
- El dato sensible (el precio) se calcula del lado del servidor con información confiable, no se recibe del cliente de la API.
- La comunicación entre servicios usa el mismo protocolo HTTP que ya conocen los estudiantes, sin introducir tecnología nueva de golpe.
