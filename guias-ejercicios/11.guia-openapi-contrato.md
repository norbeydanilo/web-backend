# Guía práctica: OpenAPI, el contrato de tu API

## Del concepto a un "hola mundo" que sirve para el proyecto final

---

## Objetivos de aprendizaje

Con esta guía buscamos que el estudiante logre:

- Explicar qué es OpenAPI, qué problema resuelve y en qué se diferencia de Swagger.
- Leer y escribir un contrato OpenAPI: rutas, parámetros, cuerpos, respuestas, errores y seguridad.
- Validar un contrato con un linter, simular una API a partir de él (mock) y comprobar que el código realmente lo cumple.
- Aplicar todo esto en el proyecto final: contrato primero, alcances (scopes) por operación y errores 401, 403, 404 y 503 declarados.

---

## 1. Qué es OpenAPI

OpenAPI es una **especificación**: un formato estándar (en YAML o JSON) para describir una API REST. Ahí se escribe, antes o después del código, qué rutas existen, qué recibe cada una, qué devuelve, qué errores puede dar y qué permiso exige.

Una forma fácil de entenderlo: el contrato de la API es lo que el plano es para una casa. El plano no es la casa, pero con él los arquitectos, los maestros de obra y los electricistas trabajan a la vez sin preguntarse a cada rato "¿y esta pared dónde va?". En nuestro proyecto, los electricistas son los otros grupos.

Tres aclaraciones que suelen confundirse:

| Término | Qué es |
| --- | --- |
| **OpenAPI** | La especificación (el formato del contrato). La versión que usaremos es la 3.0.3 |
| **Swagger** | Era el nombre de la especificación antes de la versión 3. Hoy "Swagger" se usa para las herramientas: Swagger UI (la página interactiva de documentación) y Swagger Editor |
| **AsyncAPI** | La especificación equivalente para APIs basadas en eventos (MQTT, AMQP, WebSocket). Ustedes la conocen de las exposiciones; aquí no la necesitamos |

(Hay una versión 3.1 más reciente. Usamos la 3.0.3 porque todas las herramientas de esta guía la soportan sin problemas.)

---

## 2. Para qué lo vamos a usar en el proyecto

En el proyecto, el contrato no es documentación que se escribe al final por obligación. Es la pieza que hace posible la integración, que es justamente el reto más grande:

| Uso | Cómo ayuda |
| --- | --- |
| **Acuerdo entre grupos** | El contrato vive en el repositorio del clúster. Los cambios se hacen por pull request y los aprueban quienes consumen esa API |
| **Configuración del gateway** | El gateway se configura a partir de los contratos: qué rutas enruta y qué alcance exige cada operación |
| **Mock para no esperar al vecino** | Con el contrato de otro grupo pueden simular su API desde el primer día y desarrollar su MID sin esperar a que termine |
| **Pruebas de contrato** | Una herramienta puede comprobar automáticamente que su servicio responde lo que el contrato promete |
| **Trabajo con IA** | Un contrato claro es el mejor "prompt" que existe. Si se lo dan a la IA, el código que genere encaja con el de sus compañeros. Sin contrato, cada IA inventa su propia versión |

## 3. Anatomía de un contrato

Un documento OpenAPI tiene estas secciones principales:

```
openapi        versión de la especificación (3.0.3)
info           título, versión y descripción de la API
servers        las URLs donde vive la API (local, nube, gateway)
tags           grupos para organizar las operaciones en la documentación
paths          las rutas y sus operaciones (GET, POST, ...)
components     piezas reutilizables:
  schemas          la forma de los datos (Vehiculo, Error, ...)
  responses        respuestas que se repiten (401, 403, ...)
  securitySchemes  cómo se autentica quien consume la API
```

Cinco ideas que vale la pena tener claras antes de leer el ejemplo:

- **Operación:** una combinación de ruta y método, por ejemplo `GET /vehiculos/{id}`. Cada una lleva un `operationId` (un nombre único, como `obtenerVehiculo`) que sirve para generar código y para identificarla en las pruebas.
- **Parámetros:** pueden ir en la ruta (`in: path`, como el `{id}`), en la consulta (`in: query`, como `?estado=disponible`) o en cabeceras (`in: header`).
- **Esquema (schema):** describe la forma de un dato: tipo, campos obligatorios, valores permitidos, mínimos y máximos. Es lo que permite validar automáticamente.
- **`$ref`:** una referencia para reutilizar. En vez de repetir el esquema de `Vehiculo` en cinco lugares, se define una vez en `components` y se apunta a él con `$ref: '#/components/schemas/Vehiculo'`.
- **Seguridad:** `securitySchemes` define el mecanismo (en el proyecto, OAuth2 Client Credentials) y cada operación declara con `security` qué **alcances** (scopes) exige.

## 4. Un contrato de ejemplo

Este contrato describe el CRUD de vehículos del grupo Flota del clúster Rodar (versión reducida: tres operaciones más la verificación de salud). Léanlo completo una vez y después revisamos las partes importantes.

Archivo `contrato.yaml`:

```yaml
openapi: 3.0.3
info:
  title: API de Vehículos (Flota)
  version: 1.0.0
  description: Contrato del CRUD de vehículos del grupo Flota.
servers:
  - url: http://localhost:3000
    description: Local
tags:
  - name: Vehículos
    description: Operaciones sobre la flota
  - name: Sistema
    description: Operaciones de verificación
paths:
  /health:
    get:
      summary: Verifica que el servicio está vivo
      tags: [Sistema]
      operationId: health
      security: []
      responses:
        '200':
          description: El servicio responde
          content:
            application/json:
              schema:
                type: object
                properties:
                  estado:
                    type: string
                    example: ok
  /vehiculos:
    get:
      summary: Lista vehículos
      tags: [Vehículos]
      operationId: listarVehiculos
      security:
        - clientCredentials: [vehiculos:leer]
      parameters:
        - name: estado
          in: query
          schema:
            $ref: '#/components/schemas/Estado'
      responses:
        '200':
          description: Lista de vehículos
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Vehiculo'
        '400':
          description: Filtro inválido
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
        '401':
          $ref: '#/components/responses/NoAutenticado'
        '403':
          $ref: '#/components/responses/SinPermiso'
    post:
      summary: Crea un vehículo
      tags: [Vehículos]
      operationId: crearVehiculo
      security:
        - clientCredentials: [vehiculos:escribir]
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/VehiculoNuevo'
      responses:
        '201':
          description: Vehículo creado
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Vehiculo'
        '400':
          description: Datos inválidos
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
        '415':
          description: El cuerpo no es application/json
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
        '401':
          $ref: '#/components/responses/NoAutenticado'
        '403':
          $ref: '#/components/responses/SinPermiso'
  /vehiculos/{id}:
    get:
      summary: Obtiene un vehículo por id
      tags: [Vehículos]
      operationId: obtenerVehiculo
      security:
        - clientCredentials: [vehiculos:leer]
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
            example: veh-0001
      responses:
        '200':
          description: El vehículo
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Vehiculo'
        '401':
          $ref: '#/components/responses/NoAutenticado'
        '403':
          $ref: '#/components/responses/SinPermiso'
        '404':
          description: El vehículo no existe
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
components:
  securitySchemes:
    clientCredentials:
      type: oauth2
      flows:
        clientCredentials:
          tokenUrl: http://localhost:8080/token
          scopes:
            vehiculos:leer: Consultar vehículos
            vehiculos:escribir: Crear y modificar vehículos
  schemas:
    Estado:
      type: string
      enum: [disponible, en_viaje, mantenimiento]
    VehiculoNuevo:
      type: object
      required: [tipo, bateriaPct]
      properties:
        tipo:
          type: string
          enum: [scooter, bicicleta]
        bateriaPct:
          type: integer
          minimum: 0
          maximum: 100
          example: 78
    Vehiculo:
      allOf:
        - $ref: '#/components/schemas/VehiculoNuevo'
        - type: object
          required: [id, estado]
          properties:
            id:
              type: string
              example: veh-0001
            estado:
              $ref: '#/components/schemas/Estado'
    Error:
      type: object
      required: [codigo, mensaje]
      properties:
        codigo:
          type: string
          example: vehiculo_no_encontrado
        mensaje:
          type: string
          example: El vehículo no existe
        detalle:
          type: object
  responses:
    NoAutenticado:
      description: Token ausente, inválido o vencido
      content:
        application/json:
          schema:
            $ref: '#/components/schemas/Error'
    SinPermiso:
      description: Token válido, pero sin el alcance necesario
      content:
        application/json:
          schema:
            $ref: '#/components/schemas/Error'
```

### Qué mirar en este contrato

**Seguridad por operación.** Fíjense en estas líneas de `GET /vehiculos` y `POST /vehiculos`:

```yaml
# GET /vehiculos (consultar)
security:
  - clientCredentials: [vehiculos:leer]

# POST /vehiculos (crear)
security:
  - clientCredentials: [vehiculos:escribir]
```

El token que use quien consuma la API debe traer ese alcance. Es lo que el gateway va a comprobar, y por eso importa que quede escrito aquí. `/health` lleva `security: []`: es pública a propósito.

**Respuestas reutilizables.** Los errores `401` y `403` aparecen en todas las operaciones protegidas. Se escriben una vez en `components/responses` y se reutilizan con `$ref`. Lo mismo con el esquema `Error`: **todas las APIs del clúster responden los errores con el mismo formato** (`codigo`, `mensaje` y, si hace falta, `detalle`), y ese formato queda en el contrato.

**Reglas de validación en el esquema.** `bateriaPct` es un entero entre 0 y 100, y `tipo` solo puede ser `scooter` o `bicicleta`. Esas reglas las puede hacer cumplir una librería automáticamente, como veremos.

**`allOf`.** `Vehiculo` se construye reutilizando `VehiculoNuevo` (lo que envía quien crea el vehículo) y añadiéndole `id` y `estado` (lo que asigna el servidor). Así no se repiten campos.

**Los errores documentados son parte del contrato.** Si su API puede responder un 404, el contrato debe decirlo. Más adelante veremos por qué esto no es un detalle.

## 5. Hola mundo paso a paso

El objetivo es que, al final, tengan: un contrato válido, un mock que lo simula, un servicio que lo cumple y una prueba automática que lo comprueba. Es exactamente la rutina que van a repetir en el proyecto.

El orden de trabajo es este:

```
1. Escribir el contrato
2. Validarlo con un linter          (Spectral)
3. Simularlo con un mock            (Prism)   <- los consumidores ya pueden trabajar
4. Implementar el servicio          (Node o FastAPI)
5. Comprobar que cumple el contrato (Schemathesis)
```

### Requisitos previos

- Node.js 18 o superior (también lo necesitan los grupos que programan en Python, pero solo para las herramientas del paso 2 y 3).
- Python 3.10 o superior para el paso 5 (también lo necesitan los grupos que programan en Node, solo para esa herramienta). Si no quieren instalar nada, las tres herramientas tienen imagen de Docker.
- Un editor. Recomendado: Visual Studio Code con la extensión "OpenAPI (Swagger) Editor". También sirve el editor en línea de Swagger (editor.swagger.io): pegan el YAML y ven la documentación al lado.

### Paso 1: crear el proyecto y escribir el contrato

```bash
mkdir flota-api
cd flota-api
```

Guarden el contrato de la sección 4 como `contrato.yaml` en esa carpeta.

### Paso 2: validar el contrato con Spectral

Spectral es un **linter** para contratos: revisa que estén bien formados y que sigan buenas prácticas, igual que ESLint o Flake8 lo hacen con el código.

```bash
npm init -y
npm install --save-dev @stoplight/spectral-cli @stoplight/prism-cli
```

- **@stoplight/spectral-cli:** el linter.
- **@stoplight/prism-cli:** el servidor de mocks del paso 3.

Creen el archivo `.spectral.yaml` con las reglas del proyecto:

```yaml
extends: ["spectral:oas"]
rules:
  info-contact: off
  operation-description: off
  # Regla propia: toda operación debe declarar su seguridad (aunque sea vacía, como /health).
  operacion-con-seguridad:
    description: Cada operación debe declarar `security` (alcances o lista vacía si es pública).
    severity: error
    given: "$.paths[*][get,post,put,patch,delete]"
    then:
      field: security
      function: defined
```

Las dos primeras reglas desactivadas solo quitan advertencias que no nos interesan (contacto y descripción en cada operación). La tercera es una **regla propia** que le pedimos al contrato: toda operación debe declarar su seguridad, aunque sea vacía como en `/health`. Así nadie deja una ruta desprotegida por olvido.

Agreguen estos scripts en `package.json`:

```json
"scripts": {
  "lint:contrato": "spectral lint contrato.yaml",
  "mock": "prism mock contrato.yaml -p 4010"
}
```

Y ejecuten:

```bash
npm run lint:contrato
```

Si todo está bien, el resultado es `No results with a severity of 'error' found!`. Prueben a romperlo: borren la línea `security: []` de `/health` y vuelvan a ejecutar. Verán algo así:

```
paths./health.get   error  operacion-con-seguridad  Cada operación debe declarar `security` ...
```

### Paso 3: simular la API con un mock

Un **mock** es un servidor falso que responde lo que el contrato promete, sin que exista el código real. Es lo que le permite a un grupo desarrollar su MID contra la API de un vecino que todavía no la ha programado.

```bash
npm run mock
```

Prism queda escuchando en el puerto 4010. En otra terminal:

```bash
# Sin token: el mock aplica la seguridad del contrato
curl -i http://localhost:4010/vehiculos
# HTTP/1.1 401 Unauthorized

# Con cualquier token: devuelve el ejemplo definido en el contrato
curl -H "Authorization: Bearer cualquiera" http://localhost:4010/vehiculos
# [{"tipo":"scooter","bateriaPct":78,"id":"veh-0001","estado":"disponible"}]

# Pedirle que simule un error documentado (cabecera Prefer)
curl -i -H "Authorization: Bearer x" -H "Prefer: code=404" http://localhost:4010/vehiculos/veh-9
# HTTP/1.1 404 Not Found

# Enviar datos inválidos: el mock los rechaza
curl -i -H "Authorization: Bearer x" -H "Content-Type: application/json" \
  -d '{"tipo":"moto","bateriaPct":5}' http://localhost:4010/vehiculos
# HTTP/1.1 400 Bad Request
```

(El mock arma sus respuestas con los `example` del contrato. Por eso el cuerpo del 401 puede mostrar el ejemplo del esquema `Error`, que no es un mensaje de "no autenticado". No es un fallo: si quieren cuerpos más realistas, agreguen `examples` propios a cada respuesta.)

Dos usos inmediatos en el proyecto: **(1)** simulen el 404, el 403 y el 503 de su vecino con `Prefer: code=...` para probar el manejo de errores de su MID; **(2)** den este mismo comando a sus compañeros mientras terminan su servicio.

### Paso 4: implementar el servicio

Elijan su lenguaje. Las dos versiones hacen lo mismo: sirven la documentación a partir del contrato, rechazan peticiones que no vengan del gateway (con la cabecera `X-Gateway-Secret`, como pide el enunciado) y devuelven los errores en el formato del contrato.

#### Opción A: Node.js con Express

```bash
npm install express express-openapi-validator swagger-ui-express yaml
```

- **express:** el framework que ya conocen.
- **express-openapi-validator:** lee el contrato y **valida automáticamente** cada petición y cada respuesta contra él. Si llega un `bateriaPct` de 500, responde 400 sin que escriban una sola línea de validación.
- **swagger-ui-express:** publica la documentación interactiva (Swagger UI) en `/docs`.
- **yaml:** para leer el archivo YAML.

Estructura:

```
flota-api/
├── contrato.yaml
├── .spectral.yaml
├── package.json
└── src/
    └── server.js
```

Archivo `src/server.js`:

```javascript
const path = require("path");
const fs = require("fs");
const express = require("express");
const YAML = require("yaml");
const swaggerUi = require("swagger-ui-express");
const OpenApiValidator = require("express-openapi-validator");

const PORT = process.env.PORT || 3000;
const GATEWAY_SECRET = process.env.GATEWAY_SECRET || "secreto-local";
const rutaContrato = path.join(__dirname, "..", "contrato.yaml");

const app = express();
app.use(express.json());

// 1. Documentación interactiva generada desde el contrato.
const contrato = YAML.parse(fs.readFileSync(rutaContrato, "utf8"));
app.use("/docs", swaggerUi.serve, swaggerUi.setup(contrato));

// 2. Solo se acepta tráfico que venga del gateway (excepto /health y /docs).
app.use((req, res, next) => {
  const libre = req.path === "/health" || req.path.startsWith("/docs");
  if (libre || req.get("X-Gateway-Secret") === GATEWAY_SECRET) return next();
  res.status(403).json({ codigo: "no_gateway", mensaje: "Solo se acepta tráfico del gateway" });
});

// 3. El contrato valida cada petición y cada respuesta.
app.use(
  OpenApiValidator.middleware({
    apiSpec: rutaContrato,
    validateRequests: true,
    validateResponses: true,
    validateSecurity: false, // el gateway valida el token y los alcances
  })
);

// 4. Datos en memoria y rutas (los nombres siguen el operationId del contrato).
const vehiculos = [
  { id: "veh-0001", tipo: "scooter", bateriaPct: 78, estado: "disponible" },
  { id: "veh-0002", tipo: "bicicleta", bateriaPct: 100, estado: "en_viaje" },
];
let siguiente = 3;

app.get("/health", (req, res) => res.json({ estado: "ok" }));

app.get("/vehiculos", (req, res) => {
  const { estado } = req.query;
  res.json(estado ? vehiculos.filter((v) => v.estado === estado) : vehiculos);
});

app.get("/vehiculos/:id", (req, res) => {
  const v = vehiculos.find((x) => x.id === req.params.id);
  if (!v) return res.status(404).json({ codigo: "vehiculo_no_encontrado", mensaje: "El vehículo no existe" });
  res.json(v);
});

app.post("/vehiculos", (req, res) => {
  const nuevo = { id: `veh-${String(siguiente++).padStart(4, "0")}`, estado: "disponible", ...req.body };
  vehiculos.push(nuevo);
  res.status(201).json(nuevo);
});

// 5. Los errores de validación del contrato salen con nuestro formato de error.
app.use((err, req, res, next) => {
  const codigos = { 400: "peticion_invalida", 415: "tipo_no_soportado" };
  res.status(err.status || 500).json({
    codigo: codigos[err.status] || "error_interno",
    mensaje: err.message,
  });
});

app.listen(PORT, () => console.log(`Servicio escuchando en el puerto ${PORT}`));
```

Para ejecutarlo:

```bash
GATEWAY_SECRET=secreto-local PORT=3000 node src/server.js
```

#### Opción B: Python con FastAPI

```bash
python3 -m venv .venv
source .venv/bin/activate        # en Windows: .venv\Scripts\activate
pip install fastapi uvicorn pyyaml
```

- **fastapi:** el framework que ya conocen.
- **uvicorn:** el servidor que ejecuta la aplicación.
- **pyyaml:** para leer el archivo YAML.

FastAPI normalmente **genera** el OpenAPI a partir del código. En el proyecto lo hacemos al revés: el contrato acordado con el clúster manda, así que le decimos a FastAPI que publique **ese** archivo y no el que deduciría. Los modelos de Pydantic repiten las reglas del contrato para que el servicio las haga cumplir.

Estructura:

```
flota-api/
├── contrato.yaml
├── .spectral.yaml
├── requirements.txt
└── app/
    ├── __init__.py      (vacío)
    └── main.py
```

Archivo `app/main.py`:

```python
import os
from enum import Enum
from pathlib import Path
from typing import Literal, Optional

import yaml
from fastapi import FastAPI, HTTPException, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException
from pydantic import BaseModel, Field

GATEWAY_SECRET = os.getenv("GATEWAY_SECRET", "secreto-local")
RUTA_CONTRATO = Path(__file__).resolve().parent.parent / "contrato.yaml"

app = FastAPI(title="API de Vehículos (Flota)")


# 1. La documentación (/docs) y /openapi.json salen del contrato escrito a mano,
#    no de lo que FastAPI deduciría del código.
def openapi_del_contrato():
    if app.openapi_schema is None:
        app.openapi_schema = yaml.safe_load(RUTA_CONTRATO.read_text(encoding="utf-8"))
    return app.openapi_schema


app.openapi = openapi_del_contrato


# 2. Solo se acepta tráfico que venga del gateway (excepto /health y la documentación).
@app.middleware("http")
async def solo_gateway(request: Request, call_next):
    libres = ("/health", "/docs", "/openapi.json")
    if request.url.path in libres or request.headers.get("X-Gateway-Secret") == GATEWAY_SECRET:
        return await call_next(request)
    return JSONResponse(
        status_code=403,
        content={"codigo": "no_gateway", "mensaje": "Solo se acepta tráfico del gateway"},
    )


# 3. Los modelos reflejan los esquemas del contrato (mismos nombres y reglas).
class Estado(str, Enum):
    disponible = "disponible"
    en_viaje = "en_viaje"
    mantenimiento = "mantenimiento"


class VehiculoNuevo(BaseModel):
    tipo: Literal["scooter", "bicicleta"]
    bateriaPct: int = Field(ge=0, le=100)


class Vehiculo(VehiculoNuevo):
    id: str
    estado: Estado


vehiculos = [
    Vehiculo(id="veh-0001", tipo="scooter", bateriaPct=78, estado=Estado.disponible),
    Vehiculo(id="veh-0002", tipo="bicicleta", bateriaPct=100, estado=Estado.en_viaje),
]


@app.get("/health")
def health():
    return {"estado": "ok"}


@app.get("/vehiculos", response_model=list[Vehiculo])
def listar_vehiculos(estado: Optional[Estado] = None):
    return [v for v in vehiculos if estado is None or v.estado == estado]


@app.get("/vehiculos/{id}", response_model=Vehiculo)
def obtener_vehiculo(id: str):
    for v in vehiculos:
        if v.id == id:
            return v
    raise HTTPException(status_code=404, detail="El vehículo no existe")


@app.post("/vehiculos", response_model=Vehiculo, status_code=201)
def crear_vehiculo(datos: VehiculoNuevo):
    nuevo = Vehiculo(id=f"veh-{len(vehiculos) + 1:04d}", estado=Estado.disponible, **datos.model_dump())
    vehiculos.append(nuevo)
    return nuevo


# 4. Errores con el formato del contrato (y 400, no 422, para peticiones inválidas).
@app.exception_handler(StarletteHTTPException)
async def error_http(request: Request, exc: StarletteHTTPException):
    codigos = {400: "peticion_invalida", 404: "vehiculo_no_encontrado", 405: "metodo_no_permitido"}
    codigo = codigos.get(exc.status_code, "error")
    return JSONResponse(
        status_code=exc.status_code,
        content={"codigo": codigo, "mensaje": str(exc.detail)},
        headers=exc.headers,  # conserva cabeceras como Allow en los 405
    )


@app.exception_handler(RequestValidationError)
async def error_validacion(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=400,
        content={"codigo": "peticion_invalida", "mensaje": "Datos inválidos", "detalle": {"errores": jsonable(exc)}},
    )


def jsonable(exc: RequestValidationError):
    return [{"campo": ".".join(str(p) for p in e["loc"]), "problema": e["msg"]} for e in exc.errors()]
```

Para ejecutarlo:

```bash
GATEWAY_SECRET=secreto-local uvicorn app.main:app --port 3000 --reload
```

#### Probar el servicio (cualquiera de las dos opciones)

```bash
# Salud (pública)
curl http://localhost:3000/health
# {"estado":"ok"}

# Sin la cabecera del gateway: rechazado
curl -i http://localhost:3000/vehiculos
# HTTP 403  {"codigo":"no_gateway", ...}

# Con la cabecera: funciona
curl -H "X-Gateway-Secret: secreto-local" http://localhost:3000/vehiculos

# Un vehículo que no existe
curl -i -H "X-Gateway-Secret: secreto-local" http://localhost:3000/vehiculos/zzz
# HTTP 404  {"codigo":"vehiculo_no_encontrado", ...}

# Datos inválidos (batería de 500)
curl -i -H "X-Gateway-Secret: secreto-local" -H "Content-Type: application/json" \
  -d '{"tipo":"scooter","bateriaPct":500}' http://localhost:3000/vehiculos
# HTTP 400  {"codigo":"peticion_invalida", ...}
```

Abran también `http://localhost:3000/docs`: es la documentación interactiva, generada desde el contrato.

(Fíjense en lo que **no** está en estos servicios: la validación del token. Eso lo hace el gateway. El servicio solo comprueba que la petición venga de él. Esa es la división de responsabilidades que definimos en el enunciado.)

### Paso 5: comprobar que el código cumple el contrato

Hasta aquí, el contrato y el código son dos cosas que *deberían* coincidir. Ahora lo comprobamos con **Schemathesis**, que lee el contrato, genera cientos de peticiones (válidas, inválidas y raras) y verifica que el servicio responde lo que el contrato dice.

```bash
pip install schemathesis
```

Con el servicio corriendo en el puerto 3000:

```bash
schemathesis run contrato.yaml --url http://localhost:3000 \
  -H "X-Gateway-Secret: secreto-local" \
  --checks not_a_server_error,status_code_conformance,content_type_conformance,response_schema_conformance
```

Cada `check` verifica algo distinto: que no haya errores 500, que el código de estado esté documentado, que el tipo de contenido sea el declarado y que el cuerpo cumpla el esquema. La salida correcta termina así:

```
359 generated, 359 passed
```

(El número de casos generados cambia en cada ejecución. Lo que importa es que todos pasen.)

**Lo que probablemente van a ver la primera vez.** Al preparar esta guía, la primera ejecución falló con estos problemas reales. Son típicos, y entenderlos vale más que el código:

| Qué reportó | Qué significaba | Cómo se arregló |
| --- | --- | --- |
| Código 400 no documentado en `GET /vehiculos` | El servicio rechaza un `estado` inválido con 400, pero el contrato solo prometía 200, 401 y 403 | Se agregó la respuesta 400 al contrato (el comportamiento era correcto, el contrato estaba incompleto) |
| Respuesta con `{"detail": "..."}` en lugar de nuestro error | Con un cuerpo que ni siquiera es JSON, FastAPI respondía con su propio formato, no con `codigo` y `mensaje` | Se registró el manejador de errores en la clase base de excepciones HTTP de Starlette (el código quedó corregido en esta guía) |
| Código 415 no documentado en `POST /vehiculos` (Node) | Enviar un cuerpo con otro `Content-Type` produce 415 y el contrato no lo decía | Se agregó la respuesta 415 al contrato y al manejador de errores |

La lección: **el contrato y el código se corrigen mutuamente.** A veces el error está en el código y a veces en el contrato. Lo que no puede pasar es que digan cosas distintas, porque entonces otro grupo programa contra una promesa falsa.

(Schemathesis tiene otros checks más estrictos sobre detalles del protocolo HTTP, como la cabecera `Allow` en los 405. Para el proyecto nos quedamos con los cuatro de arriba. Si quieren explorar los demás, quitan el parámetro `--checks`.)

## 6. Cómo encaja con el gateway y con los otros grupos

### Dónde viven los contratos

```
repositorio-del-cluster/
├── contratos/
│   ├── flota.yaml
│   ├── cuentas.yaml
│   └── viajes-y-zonas.yaml
├── gateway/
│   └── (configuración del gateway)
├── GATEWAY.md
└── .github/workflows/
```

Cada grupo mantiene en su propio repositorio el `contrato.yaml` que usa para programar, y el del repositorio del clúster es la **versión acordada**. Los cambios al del clúster van por pull request y los aprueban los grupos que lo consumen (así lo exige el enunciado). Si un cambio rompe a un consumidor, se descubre en la revisión y no en la demostración.

### Qué toma el gateway del contrato

- Las **rutas** que debe enrutar hacia cada servicio.
- El `securitySchemes` y el `security` de cada operación: qué alcance exige cada una. Por eso el contrato es la fuente de verdad de los permisos.
- Los **errores** que debe devolver (401 y 403 son del gateway, 404 es del servicio dueño del dato, 503 es del gateway o del consumidor).

### La URL del contrato en el clúster

En `servers` del contrato que consumen los otros grupos, la URL es la del **gateway**, no la del servicio:

```yaml
servers:
  - url: https://gateway-rodar.ejemplo.com/flota
    description: A través del gateway del clúster
```

Recuerden que ningún servicio llama a otro directamente.

### Declarar un MID con errores de negocio y de dependencias

Un MID depende de otras APIs, y el contrato debe dejar claro cómo falla. Ejemplo reducido del endpoint de recomendación del grupo Flota:

```yaml
/recomendaciones/vehiculo:
  get:
    summary: Recomienda el mejor vehículo cercano
    operationId: recomendarVehiculo
    tags: [Recomendaciones]
    security:
      - clientCredentials: [vehiculos:leer]
    parameters:
      - name: lat
        in: query
        required: true
        schema: { type: number, minimum: -90, maximum: 90 }
      - name: lng
        in: query
        required: true
        schema: { type: number, minimum: -180, maximum: 180 }
    responses:
      '200':
        description: Hasta 3 vehículos recomendados (lista vacía si no hay candidatos)
      '400':
        description: Coordenadas inválidas
        content:
          application/json:
            schema: { $ref: '#/components/schemas/Error' }
      '401': { $ref: '#/components/responses/NoAutenticado' }
      '403': { $ref: '#/components/responses/SinPermiso' }
      '503':
        description: >
          Viajes y zonas no responde. No se recomienda sin validar las zonas
          prohibidas, por eso se devuelve el error en vez de una lista parcial.
        content:
          application/json:
            schema: { $ref: '#/components/schemas/Error' }
```

Lo importante es el `503` con su explicación: ahí queda escrito el **plan de degradación** (qué hace el MID cuando falla una dependencia). Lo mismo aplica al API de tercero: si falla y su servicio devuelve un valor por defecto o un 503, el contrato lo declara.

### Qué hace quien consume el contrato de otro grupo

1. Descarga el contrato del vecino (del repositorio del clúster).
2. Levanta un mock con Prism: `npx prism mock contratos/viajes-y-zonas.yaml -p 4011`.
3. Programa su MID contra ese mock, simulando errores con `Prefer: code=404`, `code=403` y `code=503`.
4. Cuando el vecino despliega, cambia la URL (variable de entorno) y vuelve a probar.

Así nadie queda bloqueado esperando a otro.

## 7. Automatizarlo en el pipeline (por pull request)

Recuerden que todo el flujo de GitHub Actions se dispara por **pull request**, no por `push`. Este workflow valida el contrato y comprueba que el servicio lo cumple, cada vez que se abre o actualiza un pull request. Guárdenlo como `.github/workflows/contrato.yml` en el repositorio del grupo:

```yaml
name: Validar contrato

on:
  pull_request:
    branches: [main]

jobs:
  contrato:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Instalar herramientas
        run: |
          npm install --save-dev @stoplight/spectral-cli
          pip install schemathesis

      - name: Linter del contrato
        run: npx spectral lint contrato.yaml

      # Instalen aquí las dependencias de su servicio y levántenlo en segundo plano.
      # Con Node:
      - name: Levantar el servicio
        run: |
          npm install
          GATEWAY_SECRET=secreto-ci PORT=3000 node src/server.js &
          sleep 3

      - name: Pruebas de contrato
        run: |
          schemathesis run contrato.yaml --url http://localhost:3000 \
            -H "X-Gateway-Secret: secreto-ci" \
            --checks not_a_server_error,status_code_conformance,content_type_conformance,response_schema_conformance
```

(Para un servicio en Python, reemplacen el paso "Levantar el servicio" por la instalación con `pip install -r requirements.txt` y `GATEWAY_SECRET=secreto-ci uvicorn app.main:app --port 3000 &`.)

Si el linter o las pruebas fallan, el pull request no se puede fusionar (activen esa regla en la protección de la rama `main`). Para el repositorio del clúster, basta con el paso del linter aplicado a todos los archivos de `contratos/`.

## 8. Cómo usar la IA con el contrato

Ustedes desarrollan con IA, así que esto les ahorra mucho tiempo, con una condición: el contrato lo revisan ustedes.

**Para generar el borrador del contrato**, un prompt que funciona:

```
Escribe un contrato OpenAPI 3.0.3 en YAML para un API de vehículos compartidos.
Recursos: vehículos (id, tipo scooter o bicicleta, bateriaPct de 0 a 100, estado).
Operaciones: listar con filtros, obtener por id, crear, actualizar y eliminar.
Seguridad: OAuth2 clientCredentials con alcances vehiculos:leer y vehiculos:escribir,
declarados por operación.
Errores: todas las operaciones protegidas documentan 401 y 403. Todos los errores
usan el esquema Error con codigo, mensaje y detalle opcional.
Usa $ref para esquemas y respuestas reutilizables y agrega operationId a cada operación.
```

**Para generar el código**, adjunten el contrato y pidan: "Implementa este contrato en Express (o FastAPI), sin cambiar rutas, nombres de campos ni códigos de respuesta".

**Qué revisar siempre** (las IA fallan en esto con frecuencia):

- Que no hayan **inventado campos** que no están en el contrato, o cambiado nombres (`bateriaPct` por `battery`).
- Que no hayan **olvidado los errores**: 400, 401, 403, 404. Es lo que más se pierde.
- Que no hayan puesto los **alcances** equivocados, o que falte el `security` en alguna operación.
- Que el código devuelva **exactamente** los códigos de estado que dice el contrato.

Y la comprobación definitiva no es leer: es correr el linter y Schemathesis.

## 9. Errores frecuentes

| Problema | Causa habitual | Qué hacer |
| --- | --- | --- |
| El linter falla con un error de `$ref` | La ruta del `$ref` está mal escrita (`#/components/schema/...` en vez de `schemas`) | Revisen la ortografía exacta de la ruta |
| YAML que "no parsea" | Sangría con tabuladores o espacios inconsistentes | YAML solo admite espacios, 2 por nivel, sin tabuladores |
| El mock responde 401 aunque envío un token | Falta la cabecera exacta `Authorization: Bearer ...` | Revisen que el nombre de la cabecera y el prefijo `Bearer` sean correctos |
| Schemathesis reporta "response violates schema" | El servicio devuelve un campo de otro tipo, o un campo obligatorio falta | Compárenlo con el esquema; arreglen el código o el contrato |
| FastAPI responde 422 en vez de 400 | Es el código por defecto de FastAPI para datos inválidos | Registren el manejador de `RequestValidationError` como en el ejemplo |
| Cambié el contrato y el vecino dejó de funcionar | Cambio incompatible sin avisar | Todo cambio por pull request en el repositorio del clúster, aprobado por los consumidores |
