# Ficha comparativa: Azure API Management (APIM) como gateway del clúster

Esta ficha es una orientación, no una guía práctica. No hay laboratorio y su contenido **no fue probado** por el profesor. Sirve para decidir si vale la pena que un clúster intente APIM en lugar de KrakenD o del gateway propio. Las cifras de dinero no están aquí a propósito: cámbienlas por lo que muestre la calculadora de precios de Azure el día que decidan.

## 1. Qué es y qué les daría

APIM es el gateway administrado de Azure. Publica sus APIs, valida tokens, aplica políticas (límites, cabeceras, reescritura de rutas) y muestra métricas. Para este proyecto les cubre lo mismo que el gateway del clúster:

- Importar el contrato OpenAPI de cada servicio y exponerlo bajo un prefijo.
- Rechazar con 401 un token ausente, vencido o mal firmado, con la política `validate-jwt`.
- Exigir scopes por operación.
- Inyectar la cabecera `X-Gateway-Secret` con `set-header`.

Lo que **no hace**: emitir tokens. APIM valida, no es un servidor de autorización. Alguien más debe emitirlos.

## 2. Niveles que importan para un curso

| Nivel | Para qué sirve en el curso | Advertencia |
|---|---|---|
| Consumption | Pago por uso, rápido de crear | Sin integración con Entra para el portal de desarrolladores |
| Developer | Pruebas y evaluación | No es para producción y no tiene SLA |
| Basic v2 | Desarrollo y pruebas, con SLA | Es el punto de partida razonable |
| Standard v2 | Producción, integración con red virtual | Casi seguro es más de lo que necesitan |

Precios aproximados: **verificar en la calculadora de Azure**. Un APIM encendido consume el crédito de la suscripción de estudiante aunque nadie lo use, así que se crea el día de la demo y se borra después.

## 3. Dos formas de armarlo

**A. Con Entra ID.** Cada servicio y cada cliente se registra como aplicación en Entra, que emite los tokens, y APIM los valida con `validate-azure-ad-token` o `validate-jwt`. Es el camino "de manual", pero exige crear registros de aplicación. En muchos tenants universitarios esa opción está bloqueada para estudiantes: Entra permite por defecto que cualquier usuario registre aplicaciones, pero el administrador puede cambiarlo, y varias consultas de estudiantes reportan justo ese bloqueo. **Prueba de 2 minutos antes de elegir A**: intentar crear un registro de aplicación en el portal. Si falla, vayan a B.

**B. Híbrido (recomendado si A está bloqueado).** El emisor de tokens del clúster (el de las guías de KrakenD y de gateway propio) sigue emitiendo JWT firmados con HS256. APIM solo valida:

```xml
<inbound>
  <validate-jwt header-name="Authorization" require-scheme="Bearer"
                failed-validation-httpcode="401">
    <issuer-signing-keys>
      <key id="clave-1">BASE64_DEL_SECRETO</key>
    </issuer-signing-keys>
    <audiences><audience>api-cluster</audience></audiences>
    <issuers><issuer>emisor-cluster</issuer></issuers>
    <required-claims>
      <claim name="scope" match="any" separator=" ">
        <value>vehiculos:leer</value>
      </claim>
    </required-claims>
  </validate-jwt>
  <set-header name="X-Gateway-Secret" exists-action="override">
    <value>{{gateway-secret}}</value>
  </set-header>
  <base />
</inbound>
```

Detalles que hay que cuidar:

- La clave simétrica va **codificada en Base64 dentro de la política**. Cualquiera con acceso de escritura a la política la ve. Usen un valor con nombre (Named value) marcado como secreto.
- El `id` de la clave sirve para casar con el `kid` del token. Es opcional.
- La política exige la reclamación `exp`, salvo que se desactive. Nuestro emisor ya la incluye.
- `required-claims` tiene los modos `all` y `any` y un `separator` para reclamaciones multivalor. **No verificado**: que `separator=" "` funcione con nuestro `scope` como texto separado por espacios. Si no, hay que probar emitir el scope como arreglo o validarlo con una expresión de política.
- Se puede aplicar a toda la API o solo a una operación, así que los scopes por operación son posibles.

## 4. Comparación con las otras dos opciones

| Criterio | KrakenD | Gateway propio | APIM |
|---|---|---|---|
| Costo | Cero | Cero | Consume crédito |
| Probado por el profesor | Parcialmente | Sí | No |
| Emite tokens | No | Sí | No |
| Depende de permisos en Entra | No | No | Solo en la forma A |
| Curva de aprendizaje | Media | Baja (es su código) | Media, portal y XML de políticas |
| Evidencia en el repositorio | Configuración como código | Código | Hay que exportar las políticas al repositorio |

Si eligen APIM, las políticas deben quedar versionadas en el repositorio (exportadas o definidas con plantillas), porque la rúbrica evalúa el trabajo por pull request y no por clics en el portal. Siguen siendo obligatorios `GATEWAY.md` y la justificación del líder.

## 5. Recomendación

1. Si el clúster no tiene motivos específicos, use KrakenD o el gateway propio.
2. Si quieren probar APIM, hagan primero la prueba del registro de aplicación (forma A) y, si falla, usen la forma B con el emisor del clúster.
3. Calculen el costo antes de crear el recurso y fijen una fecha para borrarlo.
